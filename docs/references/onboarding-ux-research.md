# 新手引导与设置体验调研（手机端 AI 对话工具）

> 状态：**调研记录，未做实现**。目标是为「设置 → 快速入门」的内容优化提供依据：降低新手的学习成本，而不是补功能。
>
> 调研时间 2026-11-25。对象：`ccch1mneyyy/dsh-Go`（Flutter，31k stars）、`pony-huang/Gimi`（Kotlin/Compose）、`ghorbelhamdi/buddy-android`。
>
> **范围说明**：刻意排除 Bug、闪退、安装失败、机型兼容类 issue——那些属于功能正确性，与「降低学习成本」无关。下面每一条都是「功能正常但用户不会用」。

---

## 1. 用户卡在哪：三类问题

从三个仓库的 issue 里去重后，剩余诉求高度集中，且都不是「缺功能」。

### 1.1 概念没有解释，用户不知道两个选项的区别

[#1908](https://github.com/ccch1mneyyy/dsh-Go/issues/1908)（SSH 远程主机连接流程简化）最典型。添加主机时要选「托管启动」还是「只连接」，用户原话：

> 两种模式的区别对新手不直观

同一 issue 列出完整痛点链：跨设备、五步、无自动发现、无最近记录，「每次加一台新主机都要重复上述全部步骤」。

**作者的处理方式不是补文档，而是承认这是设计问题**——issue 里标注「需产品/开发评估可行性」，改进方向第 3 条就是「在 UI 里给出更直观的说明，或自动根据远程情况推荐」。

### 1.2 一眼看不出「这一步在干什么」

[#1676](https://github.com/ccch1mneyyy/dsh-Go/issues/1676) 的根因是**摘要字段选错了**。工具行显示的是参数原文，而每次工具调用其实自带一句人话说明。代码里写的是：

```dart
// app/lib/ui/chat/tool_view.dart
arg('command') ?? arg('description') ?? ''
```

`description` 只在没有 `command` 时兜底，因此永远不显示。用户原话：

> 回看一轮对话时只能看出「跑了什么」，看不出「在干什么」，读屏软件也只能念命令。

> 这个问题对长任务影响明显：一轮几十步，回看时全是一屏命令。

**作者采纳的方向是换优先级**（`description` 优先，原文进展开），不是加新 UI 组件。用户还提了一个折中：万一担心模型自填的说明不准，至少保证展开区固定显示 `description`。

### 1.3 入口太多，找不到常用的那个

[#2019](https://github.com/ccch1mneyyy/dsh-Go/issues/2019)：「全部功能」页 6 组、30+ 条目平铺，无折叠无筛选。

> 功能太多太杂，视觉噪音大，很难快速定位常用入口。手机小屏幕上尤其明显。

用户提的三个方案（任选或组合）：分组可折叠且默认折叠不常用组、提供「仅显示常用」筛选、允许自定义分组显隐与顺序。

值得注意的是，用户自己找到了**临时绕过方案**并写进 issue：

> 用户目前靠 `composer.quickActions` + `emptyState.suggestions` 把常用功能做成输入框上方胶囊和新对话建议卡来绕过该页面，属于治标不治本。

这条信息比问题本身更有价值：**用户真正的解法是「把常用项提到最外层」，而不是「把深层页面整理好」。**

[#2021](https://github.com/ccch1mneyyy/dsh-Go/issues/2021) 是同一问题的另一个切面：希望把「社区」分组往前挪，或「将最高频入口提到首页/输入框快捷胶囊级别」。

### 1.4 附带发现：术语与视觉密度

- [#69](https://github.com/ghorbelhamdi/buddy-android/issues/69)（buddy-android）：审批按钮改成图标，理由是「To fit the space」——中文标签在窄屏放不下。
- [#1520](https://github.com/ccch1mneyyy/dsh-Go/issues/1520)：「更多设置」与上方条目粘连，缺少间距。属于纯视觉节奏问题。
- [#1821](https://github.com/ccch1mneyyy/dsh-Go/issues/1821)：正文超过 4 行折叠，点开看全文——信息密度控制。

## 2. dsh-Go 的做法：一份完整的新手引导设计

`docs/design/onboarding-parallel-setup.md`（284 行）是这批材料里质量最高的，直接记录了他们降低首启学习成本的全部取舍。以下按可借鉴程度排列。

### 2.1 用等待时间做设置，而不是让用户盯着进度条

**原流程的实测耗时**（作者贴在文档里）：

| 段 | 耗时 | 用户在干什么 |
|---|---|---|
| 解压 rootfs（150 MB → 750 MB） | 约 40 s – 2 min | **什么也不能做**，盯着光环 |
| 账号登录前启动引擎 | 2–3 s | 看「正在启动引擎」 |

**新流程**：选「本机」→ 立刻后台解压 → 外观 → 连接 DeepSeek → 解压没完就进安静的等待页。

> 步数 2 → 3，但第 2、3 步是在等待时间里做的，纯等待从一两分钟降到「设置做完后剩下的那一截」。

**不可照搬的原因**：这个方案成立的前提是「有 40 秒以上的真实等待」。我们如果没有同类等待，拆步骤只会增加点击次数。

### 2.2 每步只问一个问题，不堆说明

文档里有一张「什么不进引导」的决策表，理由栏比结论栏更有价值：

| 候选 | 结论 | 理由（原文） |
|---|---|---|
| 连接 DeepSeek | 进，放最后 | 唯一真正必要的一步 |
| 外观 | 进，放中间 | 不依赖任何东西，点一下立刻换色——等待时间里最有「回报」的事 |
| 性能模式 | 只在低端机出现 | 中高端机「自动」就是完整效果，没有可确认的，不打扰 |
| 界面语言 | 不进 | 默认跟随系统，目标用户几乎不会错；设置里随时能改 |
| 手机操控 | 不进 | 要开无障碍，引导里只能放一段说明——**违背「每步一个问题，不堆说明」** |
| 宠物 | 不进 | 要悬浮窗权限，轻量模式下默认关 |
| 可视化回复 | 不进 | 默认开，**没看过回复之前讲不清它是什么** |
| 自定义色 / 跟随壁纸 | 不进 | 引导里只放六套预设，320 dp 宽也能一行放下 |

两条可提炼的原则：

- **讲不清的东西不放进引导**（可视化回复：「没看过回复之前讲不清」）。
- **需要跳出 App 才能完成的事不放进引导**（手机操控、宠物都要去系统设置）。

### 2.3 不设「跳过」按钮

> 外观页只有「继续」，没有单独的「跳过」：选项即点即生效，默认值（跟随系统 · 雾蓝）已经在用，什么都不点按「继续」就等于跳过。再放一个「跳过」只会和「继续」做同一件事。这跟 iOS 设置助理里外观页的做法一致（只有「继续」）。

**判断标准**：只有当「继续」不足以表达“我什么都不改”时，才需要「跳过」。选项已经即点即生效、默认值已经生效的场景，两个按钮是冗余。

### 2.4 进度可见但不打扰，且不跳动

底部一枚玻璃胶囊 `◔ 运行环境 42%`，「不弹窗、不挡操作；点开是状态弹层」。

细节里有一条特别值得记：

> 槽位在并行流程的页面上**一直保留**：胶囊淡出后不收起，**按钮不会在用户手指底下跳**。

还有可访问性：

> 读屏读作「正在准备运行环境，42%」
> 文字短到 320 dp × 2 倍字号也放得下：中文最长 7 个字，英文 `Runtime 42%` / `Runtime ready` / `Install failed`

### 2.5 不许诺做不到的事

> 通知权限关着时，等待页不写「完成时会通知你」（**不许诺做不到的事**），换成原来的「全程在本机完成」。

同一个原则的另一处应用：解压中就点「账号登录」时，页面切成等待态而不是让用户点一个暂时无效的按钮。

### 2.6 中断可恢复

新增偏好 `onboarding_setup_step` 记录做到哪一页，被杀后重进回到那一页；解压没完就自动重新开始。

文档给了一张完整的状态恢复表（进程被杀 / 只划掉界面 / 已解压完 / 已有 API Key 各自回到哪一页），这种穷举是设计文档里少见的严谨。

### 2.7 按「想做什么」勾选，而不是按权限名

2026-10-28 增补的一步：「想让 DSH Go 帮你做哪些事」，**默认全不勾、可跳过**。

映射表按用户目的组织：

| 功能（用户看得懂） | 用到的系统项（用户看不懂） |
|---|---|
| 读写手机里的文件 | 文件访问 |
| 桌宠与悬浮窗 | 显示在其他应用上层 |
| 手机操控 | 通知、无障碍、后台弹出界面 |
| 后台持续运行 | 通知、忽略电池优化、厂商后台开关、自启动 |
| 语音输入 | 麦克风 |

其中「厂商后台开关」还按品牌细分：vivo 后台高耗电 / 小米省电策略 / 华为荣耀应用启动管理 / OPPO 后台行为。

**这是整份调研里对我们最有借鉴价值的一条**：用户面对的是「我想让 AI 帮我做什么」，而不是「忽略电池优化」。

### 2.8 概念解释放在选择的那一刻

勾选「手机操控」后要选确认方式，二选一、**不预选**：

> 「关键步骤先问我」（`ask`）或「全程自动」（`always`，选中时说明系统设置和权限页面、密码和验证码、DSH Go 自身仍由用户操作，银行、支付类默认不碰）

三个要点：**不预选**、**解释写在选项旁而不是前置文档**、**负面清单明确**（银行、支付类默认不碰）。

## 3. Gimi 的做法：把「能力」前置成副标题

Gimi 没有独立 onboarding，但 `AddServiceScreen.kt` 的列表项写法可直接借用：

```kotlin
PreferenceListItem(
    title = template.name,
    subtitle = template.capabilitySummary(),   // 对话 · 识别 · 合成 · 实时语音
    leadingIcon = { LLMModelServiceIcon(template.id, ...) },
)
```

`capabilitySummary()` 的实现只列**已集成的能力**，用 `·` 连接：

```kotlin
/** 模板集成能力的展示摘要：对话 · 识别 · 合成 · 实时语音（仅已集成项）。 */
```

用户在选服务商时看到的是「这个能干什么」，而不是「这个叫什么」。直接对应 §1.1 的「区别不直观」。

另一条来自代码注释：

> 多实例说明紧跟分组标题；底部不再重复展示。

即：**同一句说明只出现一次，且贴近它所解释的对象。**

## 4. 可迁移的清单

按「改动成本 / 收益」排序，供后续实现时挑选。

### 4.1 低成本、可直接做

| # | 做法 | 来源 | 对应问题 |
|---|---|---|---|
| 1 | 选项副标题写「能干什么」而非「是什么」 | Gimi | §1.1 概念不直观 |
| 2 | 检查工具/列表卡摘要字段优先级：`description` 优先，原文进展开 | dsh-Go #1676 | §1.2 看不出在干什么 |
| 3 | 有默认值且即点即生效的页面，不加「跳过」 | dsh-Go §2.3 | 冗余按钮 |
| 4 | 同一说明只出现一次，靠近被解释对象 | Gimi | 重复文案 |
| 5 | 不做得到的承诺不写（通知、自动跳转等） | dsh-Go §2.5 | 信任损耗 |

### 4.2 中等成本

| # | 做法 | 来源 | 前提 |
|---|---|---|---|
| 6 | 高频入口提到最外层（输入框胶囊、空态建议卡） | dsh-Go #2019 用户的临时方案 | 需要先确定哪些是高频 |
| 7 | 设置项按用户目的分组，而非按系统概念 | dsh-Go §2.7 | 需要一张「目的 → 设置项」映射表 |
| 8 | 长列表分组可折叠，默认折叠低频组 | dsh-Go #2019 | 分组数超过 5 时才值得 |
| 9 | 等待状态用底部胶囊，槽位常驻不跳动 | dsh-Go §2.4 | 页面里确有需要等待的动作 |

### 4.3 不建议照搬

- **并行解压那套流程**：前提是 40 秒以上的真实等待。我们没有同类场景，拆步骤只会增加点击。
- **「每步一个问题」的严格步进**：dsh-Go 的首启有强依赖（引擎未就绪则账号登录不可用），所以必须串行。我们的快速入门没有这种依赖链，串行化收益不大。
- **具体的分组内容**（宠物、可视化回复等）：是针对它们自己的功能集，不通用。

## 5. 对我们「设置 → 快速入门」的初步判断

现状：`QuickStartPage` 两个 Tab（DeepSeek / 通用），纯模型配置。

对照 §1 的三类问题：

| 问题类型 | 我们是否有 | 说明 |
|---|---|---|
| 概念不直观 | **可能有** | 「DeepSeek」与其他服务商并列，但没有说明各自能干什么、是否需要额外账号 |
| 看不出在干什么 | 部分 | 工具卡摘要用的是参数原文（与 #1676 同构） |
| 找不到常用项 | 待评估 | 取决于快速入门页的条目数量 |

具体改法（§4.1 第 1、2 条）属于文案与优先级调整，不影响结构；§4.2 第 7 条（按用途组织）会改变页面定位，需要单独决策。
